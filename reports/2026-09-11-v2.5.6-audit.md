## 4. Recording frame-rate investigation

Report: "when recording video in VM timed recording in RAV the FPS in RAV
drops hugely (2–5 fps visually), on video it all comes out ok."

### 4.1 Method

- Build: `RAV 2.6.0 DEV.app` (current tree), isolated MCP on 9278 via a stdio client, Script Access enabled for `rav_eval`.
- Visual rate: `screencapture -v` of the canvas region for 5 s, per-frame luminance difference through ffmpeg, count of frames that changed. Baseline on a continuously animating file: **~48–53 updates/s** (VFR capture caps near 55).
- In-child probe (`rav_eval`, target `playback`): RAF callback rate, native tick rate (wrapping `window.__ravNativeFrameTick`), Rive `frameCount` delta, per-tick duration grouped by frames rendered, and main-thread stall detection (4 ms timer drift > 50 ms).

### 4.2 Results

Light file (`interactive-blur-waves.riv`, ~2 ms/frame), 9 s, scheduled pointer ops:

| Format | Visual updates/s | Captured | `max_lag_ms` |
| --- | --- | --- | --- |
| H.264 1200×800 | 50.9 | 540/540 | 25 |
| H.264 scale 2 | 49.9 | 540/540 | 35 |
| WebM (VP9) | 48.7 | 540/540 | 29 |
| APNG (lossless worker) | 50.7 | 540/540 | 954 |

No visible degradation. (APNG encode of 540 frames took ~5 min and produced 437 MB; unrelated to the report but worth knowing.)

Heavy file (`teachers-pet.riv`, 874 accessors, feathers/blur), 9 s, scheduled `vm-set` enum/number writes:

| Metric | Idle | During recording |
| --- | --- | --- |
| Native ticks delivered | 0 | **58.6–60 Hz** |
| Rive frames rendered | 57/s | 37–45/s |
| RAF / compositor updates | 57 Hz | **4–9 Hz**, gaps ~200 ms |
| Main-thread stalls > 50 ms | 0 | 6–8 per second, max 229 ms |
| Tick work share of wall time | — | 76 % |
| Per-tick cost when a frame renders | — | p50 21 ms, p95 24 ms, max 29 ms |
| Ticks that rendered nothing | — | 122 of 315 (not due / encoder back-pressure) |
| Visual updates/s (screen capture) | ~48 | 21–28 |
| `max_lag_ms` at end | — | 2,470–5,400 |

Output files were complete (540/540 frames, all receipts `lateness_seconds: 0`).

### 4.3 Mechanism

The native wake lane is open-loop: `tokio::time::interval(16.667 ms)` → `webview.eval("window.__ravNativeFrameTick?.()")` with no acknowledgement. In `renderSurfaceAdvanceFrame` the child calls `player.stopRendering()` in `finally`, which cancels the runtime's own RAF re-request, so during a native-owned recording **every** wake is an eval. When one frame (render + `VideoFrame`/encode hand-off) costs ~21 ms, evals arrive faster than they complete and queue on the WebContent main thread; they run back-to-back, and WebKit's rendering update (RAF + compositing) is starved to roughly one presentation every ~200 ms. Every simulation frame is still rendered and captured, so the file is correct; only presentation suffers. The per-wake budget in `pumpRenderSurfaceRecording` (4 frames / 8 ms) does not help because the check runs after a frame, and the backlog is in the eval queue, not inside one pump.

Light files never hit it because a 2 ms frame leaves the thread idle between ticks.

### 4.4 Fix options

1. **Child-side pacing (smallest).** In `__ravNativeFrameTick`, skip pumping when the document is visible and a rendering update has not happened since the last pump (track via a RAF flag); let the child's own RAF drive the pump while visible and use native ticks only as the hidden/occluded fallback (no RAF for >100 ms). Presentation returns to one update per rendered frame (~37 fps on this file); capture throughput is unchanged.
2. **Native back-pressure.** Use `eval_with_callback` and schedule the next tick only after the previous callback returns (plus interval). Removes the queue growth but still leaves the thread saturated on heavy files unless combined with 1.
3. **Do not cancel the runtime RAF** in `renderSurfaceAdvanceFrame` during native-owned recording, so `_boundDraw` keeps pumping at display rate; requires care to avoid double-advancing.

Recommendation: 1 (plus 2 as hygiene) in the next release; both are small and testable with the probe above.

## 5. Capture pipeline rebuild — results

Implemented on 2026-09-11 in `demo-template/js/media/pipeline/` (`capture-worker.js`,
`capture-pipeline.js`, `recording-loop.js`), replacing `recording-clock.js`,
`png-encoder.js` and the main-thread `VideoFrame(canvas)` path.

Design: draw → GPU `ImageBitmap` snapshot (≤1 ms) → transferable to a capture
worker → compose/`VideoFrame`/`VideoEncoder` or PNG off-thread; one worker for
video, three for PNG with in-order delivery; a self-scheduled loop with
bounded batches (14 ms live / 24 ms offline) that yields to the compositor
(RAF, or a MessageChannel task when hidden); native ticks demoted to kicks;
`clock: live | offline`; native capture receipts pushed to the host.

Same heavy file and VM schedule as §4, `RAV 2.5.6 DEV.app`:

| Metric | Before | After (live) | After (offline) |
| --- | --- | --- | --- |
| Native ticks | 60 Hz, 21 ms each | 60 Hz, 0 ms each | 60 Hz, 0 ms |
| Main-thread stalls > 50 ms | 6–8 / s, max 229 ms | **0** | 0–2 / s, max 52 ms |
| RAF / compositor updates | 4–9 Hz | **27–30 Hz** | 26–29 Hz |
| Rive frames rendered | 37–45 / s | 40–45 / s | 40–44 / s |
| `max_lag_ms` (9 s capture) | 4,500–5,400 | 3,900 | 0 (not applicable) |
| Output | 540/540 | 540/540, 0 duplicate consecutive frames | 540/540, 0 duplicates |
| Status-bar count during capture | stale | live: 30 → 90 → 135 → 180 … | live |

Per-frame main-thread cost on this file at 2560×1440: `draw` 9 ms, snapshot
≤1 ms (was `draw` 4 ms + `VideoFrame(canvas)` 17–20 ms at 1200×800). Alpha
APNG at 1280×720 (three PNG workers): ~50 captured frames/s, RAF ~40 Hz, live
counts, 540/540 with no duplicates; native APNG encoding then took ~110 s.

Light file (`interactive-blur-waves.riv`): unchanged, ~50 visual updates/s.
